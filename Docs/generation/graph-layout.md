# Graph layout

> [DreamShader](../index.md) » [Generation](index.md) » **Graph layout**

The pass that assigns editor coordinates and comment boxes to the nodes a compile just created.

| | |
| :-- | :-- |
| Runs on | `UMaterial` (including the hidden ThinCustom base) and `UMaterialFunction` |
| Runs after | the graph is built and the outputs are connected; before the material is recompiled |
| Source control | the optional [`Layout`](../language/layout.md) section and `#Region` / `#EndRegion` |
| Produces | node positions, `UMaterialExpressionComment` boxes, `DS_Shared_*` named reroutes |

## When layout runs

| Condition | Behaviour |
| :-- | :-- |
| memory-only (transient) generation | **skipped entirely** — nodes keep their construction positions |
| fewer than 2 expressions in the graph | skipped |
| **1200 or more** expressions, and no `Layout` section | skipped, with a log line |
| a `Layout` section is present | explicit path |
| otherwise | automatic path |

The large-graph bail-out logs:

```text
Skipping automatic layout for large DreamShader graph ({Count} nodes). Existing generated positions
will be used.
```

The threshold is on the expression count of the finished graph, not on source length. It is checked
only on the automatic path — an explicit `Layout` section is always honoured, at any node count.

> [!NOTE]
> Because interactive compiles are memory-only, the graph you see in the [preview](../tools/preview.md)
> or on a not-yet-materialized material is **unlaid out**: nodes sit at the fixed coordinates the
> construction pass gave them. Layout appears when the asset is materialized, cooked, or generated by
> the commandlet. See [In-memory materials](in-memory.md).

## Explicit layout

A `Layout` section pins named variables and declares comment boxes. Full grammar, argument tables and
parse diagnostics are on the [Layout](../language/layout.md) page; this section covers what the
placement pass does with them.

```c
Layout = {
    Comment(Name="Sampling", X=-1200, Y=-200, W=900, H=400);
    Node(Var="UV", X=-1100, Y=-120);
}
```

The explicit path is taken when the `Layout` block matched at least one `Node(Var=…)` against a
generated variable, **or** declared at least one `Comment(…)`. Then, in order:

1. **Pinned nodes.** Each `Node(Var=…)` writes its expression's editor X/Y exactly, and the graph
   node's position when one exists. A `Var` that names no generated variable is ignored silently.
2. **Comment boxes.** Each `Comment(…)` creates a `UMaterialExpressionComment` at the literal X/Y
   with the given W/H. An empty or whitespace-only `Name` is skipped.
3. **Unpinned nodes** are placed by iterative propagation from their already-positioned neighbours.
4. **Reroutes** are inserted for *distant* connections that cross a block boundary.
5. **The material root** is positioned near the outputs it consumes, then the output-feeding reroute
   usages are regrouped under a `Material Output` box.

### Comment box properties

| Property | Explicit `Comment(…)` | Automatic box |
| :-- | :-- | :-- |
| Text | `DreamShader: ` + `Name` | `DreamShader: ` + block title |
| Position | literal `X`, `Y` | block bounds minus padding (110, 90) |
| Size | `max(120, W)` × `max(80, H)` | `max(420, width + 220)` × `max(240, height + 180)` |
| Colour | `Color=float4(…)` if given, otherwise `(0.10, 0.16, 0.22, 0.35)` | `(0.10, 0.16, 0.22, 0.35)` |
| Font size | 24 | 24 |
| Group mode | on | on |
| Comment bubble | visible in the details panel, coloured | visible in the details panel, coloured |

> [!WARNING]
> Every comment box DreamShader creates has its text prefixed with the literal `DreamShader: `, and
> that prefix is exactly what regeneration deletes. Writing `Comment(Name="Sampling", …)` produces a
> box reading `DreamShader: Sampling`; renaming it in the material editor to something without the
> prefix makes it survive the next rebuild — and a second box appears beside it. See
> [Regeneration](regeneration.md#what-survives).

### Placing the unpinned nodes

Propagation runs until nothing moves, capped at `max(32, pending count)` passes.

| Known neighbours | Position |
| :-- | :-- |
| both dependencies and consumers | the midpoint between them |
| consumers only | `consumerX - 360`, same Y |
| dependencies only | `dependencyX + 360`, same Y |
| neither, ever | fallback column |

Collisions are resolved by bucketing positions into 80 × 80 slots; the *n*-th occupant of a slot is
offset vertically by `±((n + 1) / 2) * 120`, alternating sign.

Anything still unplaced goes into a fallback column at `bounds.MinX - 480` (or `-1200` when nothing
was positioned), stepping Y by 180 from `bounds.MaxY + 240` (or `-620`).

## Automatic layout

With no `Layout` section, the pass partitions the graph into **blocks**, lays each block out
independently, and stacks the blocks downward.

### Block construction

Blocks are built in this order and then stable-sorted by sort key, ascending.

| Order | Block | Title | Sort key |
| :-- | :-- | :-- | :-- |
| 1 | one per distinct `#Region` name | the region name | region order |
| 2 | *(material)* one per **connected** material property input | `Output: <PropertyName>` | the material-property enum index |
| 3 | *(material function)* one per `UMaterialExpressionFunctionOutput` | `Output: <OutputName>`, or `Output: FunctionOutput` when unnamed | `1000 + declaration order` |
| 4 | every expression with no consumers that is not already a sink | `Generated Outputs` | `100000` |
| 5 | *(only if nothing above produced a block)* everything | `Graph` | `0` |
| 6 | expressions used by more than one block that no block owns | `Shared Inputs` | `-1000`, inserted first |

An expression appearing in exactly one block is assigned to it immediately. Ambiguous ones are
resolved over at most 16 passes by "which block already owns the most of my direct consumers";
leftovers take their first candidate. Every `NamedRerouteDeclaration` is finally forced into its
source's block.

### Cross-block reroutes

Any input that crosses a block boundary is rewired through a shared named reroute.

| Node | Name | Position |
| :-- | :-- | :-- |
| `UMaterialExpressionNamedRerouteDeclaration` | `DS_Shared_<n>`, `n` counting from 0 | `source.X + 360`, `source.Y` |
| `UMaterialExpressionNamedRerouteUsage` | one per (declaration, consumer block) pair | `consumer.X - 360`, fanned out vertically by `±((slot + 1) / 2) * 80` |

Input channel masks are preserved across the rewire. On the automatic path every crossing connection
is bridged; on the explicit path only **distant** ones are, where distant means `|ΔX| ≥ 900` or
`|ΔY| ≥ 540`. The explicit path additionally bails out before inserting anything unless it built at
least two blocks and assigned owners to at least two expressions.

### Placement inside a block

A layered, Sugiyama-style layout.

1. **Rank** each expression by its longest path to a consumer: sinks are rank 0, and
   `rank(e) = max(rank(consumer) + 1)`. A cycle resolves to rank 0.
2. Stable-sort each layer by current Y, breaking ties by creation order.
3. Run **4 barycenter passes**. Each pass sweeps downward, ordering by average consumer position,
   then upward, ordering by average dependency position.
4. Assign coordinates: a rank-`r` layer sits at `X = 900 - r * 420`; rows step by 220 and are
   vertically centred on `blockTop + ((maxLayerSize - 1) * 220) / 2`.

Blocks stack downward from `Y = -620`, each starting at the previous block's `bounds.MaxY + 420`.

### The material root

Two passes touch the root node, in order:

1. `RootX = combinedBounds.MaxX + 520`, `RootY = (MinY + MaxY) / 2 - 240`. The material graph's root
   node position is written too.
2. Output-feeding named-reroute **usages** are then pulled out of their computation blocks and
   stacked in a single column at `bodyBounds.MaxX + 420`, spaced 130 apart; the root moves a further
   360 to the right; and the whole group gets its own comment box titled `Material Output`.

Removing those usages from the computation blocks first is what keeps the per-property boxes tight.

## Layout constants

| Constant | Value | Applies to |
| :-- | :-- | :-- |
| Output column X | `900` | rank-0 layer, and `FunctionOutput` nodes |
| Column spacing | `420` | X step per rank |
| Row spacing | `220` | Y step within a layer |
| Block spacing | `420` | gap between stacked blocks |
| First block top | `-620` | Y of the first block |
| Node footprint | `320 × 150` | bounds computation |
| Comment padding | `110` X, `90` Y | automatic boxes |
| Minimum automatic box | `420 × 240` | automatic boxes |
| Minimum explicit box | `120 × 80` | `Comment(…)` |
| Reroute offset | `360` | declaration right of source, usage left of consumer |
| Reroute fan-out | `±((slot + 1) / 2) * 80` | stacked usages |
| Root gap | `520` | root right of the graph bounds |
| Output-usage column | `bodyBounds.MaxX + 420`, spacing `130`, root `+360` | the `Material Output` group |
| Distant threshold | `|ΔX| ≥ 900` or `|ΔY| ≥ 540` | explicit path reroutes only |
| Barycenter passes | `4` | per block |
| Owner-assignment passes | `≤ 16` | ambiguous expressions |
| Propagation passes | `max(32, pending)` | explicit path, unpinned nodes |
| Large-graph threshold | `1200` | automatic-layout bail-out |

> [!NOTE]
> These constants are not part of the stable surface. The generated-asset layout may change before
> the stable 1.5.0 release; nothing in a `.dsm` depends on them except through a `Layout` section,
> which pins absolute coordinates and is unaffected.

## `Output:` block titles

The material-property block titles come from a fixed table. Every name below produces
`Output: <name>`; anything not listed produces `Output: MaterialProperty<enum index>`.

`BaseColor`, `MaterialAttributes`, `EmissiveColor`, `Opacity`, `OpacityMask`, `Metallic`,
`Specular`, `Roughness`, `Normal`, `AmbientOcclusion`, `Refraction`, `WorldPositionOffset`,
`PixelDepthOffset`, `SubsurfaceColor`, `CustomData0`, `CustomData1`, `DiffuseColor`,
`SpecularColor`, `SurfaceThickness`, `Displacement`, `CustomizedUV0`, `CustomizedUV1`,
`CustomizedUV2`, `CustomizedUV3`, `CustomizedUV4`, `CustomizedUV5`, `CustomizedUV6`,
`CustomizedUV7`, `Anisotropy`, `Tangent`.

A custom engine build that defines `MOON_ENGINE` adds five more:
`MooaEncodedAttribute0` … `MooaEncodedAttribute4`. Stock UE 5.3 – 5.8 does not.

## Construction-time positions

These are the coordinates nodes carry when layout is skipped — memory-only generation, a graph of
fewer than two nodes, or 1200 or more nodes with no `Layout` section.

| Node | X | First Y | Y step |
| :-- | :-- | :-- | :-- |
| whole-surface `Custom` node (material) | `120` | `0` | — |
| whole-surface `Custom` node (material function) | `120` | `0` | — |
| `MakeMaterialAttributes` seed (material) | `120` | `200` | `+220` |
| `MakeMaterialAttributes` seed (material function) | `120` | `260` | `+220` |
| property / parameter node — material `Custom` path | per node | `-300` | `+220` |
| property node — material-function `Custom` path | per node | `-620` | `+220` |
| property node — `Graph` path | per node | `-620` | `+220` |
| general `Graph` node | per node | `-120` | `+180` |
| `FunctionInput` | `-800` | `-260` | `+180` |
| `FunctionOutput` | `900` | `-120` | `+180` |
| `Expression(…)` output-target node | `1200` | `200` | `+220` |
| scalar / vector literal constant | `-1120` | from the caller | — |

Every `Outputs` binding also creates a named-reroute pair at construction time: the declaration at
`source.X + 420`, `source.Y`, and the usage at `X = 720`, `Y = -120 + max(routeIndex, 0) * 180`. The
declaration is named `DS_<sanitized route name>`, plus `_<index>` when the route is indexed;
a blank route name falls back to `DS_Output`.

## Notes

- `#Region "Name"` / `#EndRegion` in a `Graph` block do not move anything by themselves — they name
  blocks for the automatic path. Regions nest, and directive lines are blanked out so reported line
  numbers stay correct. Grammar and diagnostics are on the [Layout](../language/layout.md) page.
- A `Layout` section with only `Node(Var=…)` entries that match nothing, and no `Comment(…)`, does
  **not** engage the explicit path — the automatic path runs instead.
- A second `Layout` section in the same block replaces the first entirely.
- Layout positions are not preserved across regeneration. A `Layout` section is the only way to make
  a node's position stable. See [Regeneration](regeneration.md).
- The [decompiler](../tools/decompiler.md) emits a `Layout` section in exactly the parse format, so a
  hand-arranged material can be exported and re-imported with its arrangement intact. This is
  controlled by the **Export Decompiled Layout** project setting, default on.
- Automatic layout reports one slow-task frame per node, titled
  `Laying out DreamShader material graph...` with frame text `Positioning node {N} of {Total}...`.

## Example

```c
Shader(Name="Docs/M_Layout")
{
    Properties {
        vec3  Tint      = vec3(1.0, 0.4, 0.1);
        float Intensity = 2.0;
    }
    Settings { Domain = "UI"; ShadingModel = "Unlit"; }
    Outputs  {
        vec3  Color;
        float Alpha;
        Base.EmissiveColor = Color;
        Base.Opacity       = Alpha;
    }
    Graph {
        #Region "Colour"
        Color = Tint * Intensity;
        #EndRegion
        #Region "Alpha"
        Alpha = Intensity * 0.5;
        #EndRegion
    }
}
```

Automatic layout produces:

```text
comment  DreamShader: Shared Inputs        sort key   -1000
comment  DreamShader: Colour               sort key   region order
comment  DreamShader: Alpha                sort key   region order
comment  DreamShader: Output: EmissiveColor
comment  DreamShader: Output: Opacity
comment  DreamShader: Material Output      root + the output reroute usages
reroute  DS_Shared_0                       Intensity, used by two blocks
```

Pinning one node instead:

```c
    Layout = {
        Comment(Name="Colour", X=-1200, Y=-200, W=900, H=400);
        Node(Var="Color", X=-600, Y=-120);
    }
```

```text
comment  DreamShader: Colour               at (-1200, -200), 900 x 400
node     Color                             at (-600, -120), exactly
                                           every other node propagated from its neighbours
```
